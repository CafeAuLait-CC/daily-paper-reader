Abstract: Robot foundation models increasingly rely on flow-based action gen-eration for general-purpose manipulation, yet the generated actions are not guar-anteed to satisfy physical constraints such as joint limits and collision avoidance. This problem is especially challenging when the feasible set cannot be described analytically and is accessible only through black-box feasibility oracles. We study this practical oracle-only setting and propose an oracle-guided differentiable safe-guard for safe flow-matching robot policies. The safeguard uses binary feasibility queries to correct unsafe updates in the forward pass, while extracting local bound-ary information to provide constraint-aware learning signals in the backward pass. Combined with discrete-time flow matching, the same safeguard is used during training and inference, enabling forward–backward aligned policy learning with-out explicit or differentiable constraint models. Experiments on obstacle-aware robotic manipulation demonstrate 100% constraint satisfaction while preserving task performance. 

Keywords: safe robot learning, flow matching, feasibility oracle 

## 1 Introduction 

Robot foundation models, including vision-language-action (VLA) models [1, 2] and world-action models (WAMs) [3, 4], increasingly combine pretrained vision-language or video-generation back-bones with flow-based action generation for general-purpose robot control. However, strong task generalization does not guarantee safe physical interaction: generated actions must also satisfy con-straints such as joint limits and collision avoidance. Enforcing such scene-dependent constraints remains a key challenge for deploying flow-based robot policies. Existing methods either correct generated actions only at inference time or incorporate constraint en-forcement into training. Inference-time correction, e.g., through control barrier functions [5, 6, 7, 8], or trajectory-wise constraint guidance [9, 10], can be applied to pretrained policies but introduces a train–test mismatch. Training-aware approaches reduce this mismatch [11, 12, 13], but typically re-quire explicit constraint functions, differentiable constraint models, or known feasible-set geometry. Such information is often difficult to obtain in robotics. For example, in robotic arm obstacle avoid-ance, a collision checker can readily determine whether a candidate configuration is feasible, while an analytical description of the corresponding collision-free configuration space may be unavailable. This motivates an oracle-only setting, where safety is accessible solely through a binary feasibility oracle. We ask: how can a flow-matching robot policy enforce constraints and learn from them when only binary feasibility queries are available? To address this problem, we propose an oracle-guided differentiable safeguard . In the forward pass, the safeguard uses oracle queries to restrict each predicted update to the feasible region. In the backward pass, it extracts local boundary information from nearby binary queries and uses it to construct a boundary-aware surrogate gradient. Thus, arXiv:2610.40075v1 [cs.RO] 29 Oct 2026 the same oracle supports both feasibility enforcement and constraint-aware policy learning, without requiring an explicit or differentiable constraint model. We integrate the safeguard with discrete-time flow matching, allowing the same correction mecha-nism to be used during both training and inference. This yields a forward–backward aligned learning framework in which the policy is optimized under the safety intervention encountered at deployment. Our contributions are summarized as follows: • We formulate safe flow-matching robot policy learning under an oracle-only constraint interface, removing the need for explicit or differentiable constraint models. • We introduce an oracle-guided differentiable safeguard that combines oracle-based for-ward feasibility correction with boundary-aware surrogate gradients, enabling forward– backward aligned policy learning. • We validate the proposed approach on an obstacle-aware robotic manipulation task, demon-strating strong constraint satisfaction while maintaining task performance.

## 5 Conclusion 

We propose an oracle-guided differentiable safeguard for safe flow-matching robot policies using only binary feasibility feedback. The oracle enforces feasibility in the forward pass and provides local boundary information for backward learning, allowing the same safeguard to be used during training and inference without explicit or differentiable constraint models. Experiments on obstacle-aware manipulation show improved safety while preserving task performance and motion quality. A current limitation is that the discrete flow still relies on simple interpolation paths, which may become unreliable in highly non-convex feasible regions. ## B Practical Implementation 

Forward: coarse scanning and local bisection. Given xk and dk, we first query the oracle at uniformly spaced points along rk(α) = xk + αd k, with α ∈ [0 , 1] . If all sampled points are feasible, the full update is accepted. Otherwise, the first sampled infeasible point and its preceding feasible point define a local search interval. Then we refine this interval by bisection. The final feasible endpoint approximates the first-exit point.

## C Experimental Details 

Expert data collection. We collect demonstrations with a collision-aware MPlib planner. Inverse kinematics first provides candidate grasp configurations, after which RRT plans joint-space motions to the pre-grasp and pre-place poses. Local Cartesian planning completes the short approach and placement motions. Once the grasp is physically verified, the bottle geometry is attached to the end effector in the planning scene so that subsequent transport accounts for the carried object. The planner also uses a 4 cm inflated obstacle envelope to leave clearance along the planned motion. We retain successful, safety-checked episodes and replay their stored joint paths to record synchronized observations, actions, and privileged scene information, yielding the 150 demonstrations used in Table 1. 

Oracle implementation. The recorded scene information supports a batched JAX feasibility ora-cle that combines joint-limit checks with collision checks. For each queried configuration, forward kinematics transforms sphere approximations of the left-arm links into world coordinates, where they are checked against the scene geometry. During transport, the carried bottle is placed using the candidate end-effector pose and the observed object-to-end-effector transform, allowing its col-lisions to be checked as well. The safeguard accesses the resulting binary feasibility labels without differentiating through the checker. 7Feasible initial distribution. We construct p0(· | ot) by randomly sampling joint configurations in a local neighborhood of the currently observed joint state and retaining candidates that satisfy the oracle constraints. An accepted configuration is repeated across the horizon to form X0. The same initialization procedure is used during training and inference, providing a feasible starting point for the safeguarded flow. 

Training parameters. All variants are fine-tuned with LoRA for 30K updates on a single H100 GPU, using a batch size of 32. We use AdamW with (β1, β 2) = (0 .9, 0.95) , ϵ = 10 −8, weight decay 

10 −10 , and gradient clipping at 1.0. The learning rate increases to 2.5 × 10 −5 over 1K warmup steps and then follows a cosine schedule, with the decay step set to 20K and a final rate of 2.5 × 10 −6.An exponential moving average of the parameters is maintained with decay 0.99. 

## D Discussion and Limitations 

D.1 Why Maintain Feasibility at Every Generation Step? 

Intermediate flow states are not executed by the robot, so their feasibility is an algorithmic choice rather than a physical execution requirement. We make this choice to construct a generation process that remains within the feasible set: starting from a feasible sample, each safeguarded update pre-serves feasibility, which in turn ensures that the final output satisfies the constraints. This shares the feasible-iterate motivation of interior-point methods, although our method uses oracle-based correc-tion rather than a barrier objective. Maintaining generation trajectories within a constrained domain is also central to reflected flow matching [19], which uses boundary reflection. The resulting discrete invariance of our method is stated below. 

Proposition 1 (Fixed-context feasibility preservation) . For a fixed context ξt, suppose X0 ∈ C (ξt)H

and each horizon-wise update returns an oracle-verified feasible configuration or retains its feasible input. Then Xk ∈ C (ξt)H for every k = 0 , . . . , T .

The claim follows by induction, since the forward search returns a checked feasible point at each step. Applying the same correction during training also exposes the policy to the interventions it encounters during inference. Together, these choices align policy learning with feasible generation and make final configuration feasibility a property of the sampling procedure, without requiring a separate terminal projection. 

D.2 What Are the Main Limitations? Feasible data, initialization, and local geometry. The formulation assumes that the target action distribution lies within the feasible set and that feasible initial samples can be obtained. With linear reference paths, these endpoint conditions must be accompanied by local feasible connectivity: a sufficient condition is that each source–target pair lies within a common convex feasible neighbor-hood. In a non-convex region, a straight reference path may instead cross an obstacle even when both endpoints are feasible, creating supervision that the safeguarded update cannot follow. The forward correction also preserves the predicted direction, so it cannot independently select a route around the obstacle. These limitations motivate reference paths that better capture feasible task geometry. 

Oracle fidelity and computational cost. The practical correction depends on finite scans and local probes, whose resolution limits how accurately they capture complex boundaries. Its safety scope is therefore determined by the oracle and the configurations actually checked. Increasing the query budget can improve boundary resolution, but also increases computation. In Table 1, the full method requires 1.345 s per chunk compared with 0.071 s for the Gaussian baseline, approximately 

18 .9× as long. Reducing this overhead while retaining reliable feasibility checks is necessary for more responsive manipulation. 8D.3 Future Directions 

A natural next step is to replace straight reference paths with nonlinear paths that remain within the feasible region. Riemannian flow matching [20] illustrates how known manifold geometry can inform the construction of target vector fields; in our oracle-only setting, feasible expert trajecto-ries offer a practical source of path information. The reference can follow the demonstrated route around obstacles rather than directly interpolate between the initial sample and each target config-uration. With feasible local connections, this could extend the approach to non-convex constraint regions while retaining the same oracle-guided safeguard. The remaining challenge is to connect randomly sampled initial configurations to these paths and discretize them without introducing in-feasible shortcuts. A complementary direction is to reduce the cost of oracle queries during generation. Adaptive coarse scanning and selective local refinement could concentrate queries near detected boundaries, while more efficient batched collision checking could reduce their latency. Evaluating these strategies jointly with task success and constraint satisfaction would help identify a practical balance between computational cost and safety for online manipulation. 9
